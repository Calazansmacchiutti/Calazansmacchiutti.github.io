Project Overview

The core system is an agent that structures PDFs for retrieval-augmented generation. Printed-text OCR handles typed pages, but handwriting it cannot - and no public HTR model exists for Brazilian Portuguese. So I built the handwriting reader from scratch and plugged it in behind the same interface as the existing OCR, selectable at runtime. Nothing downstream needs to know whether a page was typed or handwritten.

Main Products / Deliverables

pt-BR HTR model

A versioned artifact (weights + alphabet, sha256), 4.3M params, 17 MB - CPU-friendly inference, no GPU required to serve.

Pluggable reading backend

A drop-in OCR/HTR reader behind available() + ocr_blocks(), swappable with Tesseract without touching the pipeline.

Document-to-answer pipeline

PDF structuring, vector retrieval, and an agentic RAG loop that turns scanned documents into cited answers.

Reproducible bakeoff harness

The evaluation and promotion-gate system that picks models by metric - plus a parametrized Colab notebook for managed GPU training.

Key Questions Answered

  • Can a competitive Portuguese handwriting reader be trained with no pre-existing model and no local GPU?
  • Which architecture actually wins - decided by a metric on the official split, not by intuition?
  • How does a research model become a swappable component of a cloud pipeline?

Methodology - how the 9.57% was reached

The number is not from a lucky run; it is the output of a disciplined, reproducible procedure. The metric was written before the models: CER is aggregated across the corpus (edits and lengths summed before dividing, exactly as in the ICDAR 2024 evaluation) so the result is directly comparable to published work.

  1. Fixed the ground rules. Official BRESSAY splits (19,565 train / 4,609 validation lines), never a custom partition. The alphabet (96 classes) is built from the training split only, by frequency, and travels with the checkpoint - desynchronized indices would make the model "read another language".
  2. Framed a bakeoff with a promotion gate. Each architecture trains on the same data and is ranked by validation CER; a challenger only replaces the baseline if it beats that CER. The baseline is CRNN + CTC (no autoregressive decoder, so it cannot hallucinate); the challenger is a fine-tuned TrOCR.
  3. Trained with stable, cheap choices. Adam (lr 1e-3), ReduceLROnPlateau on validation CER, gradient clipping at 5.0, batch 24, and - critically - the checkpoint saved is the best epoch, not the last. Resumes are anchored to the loaded model's CER so a noisy first epoch never overwrites a good checkpoint.
  4. Read the curve, not the folklore. The CER oscillated in epochs 8 - 10; the wrong reading was "overfitting". The right one was learning rate too high - cutting it 1e-3→5e-4 unlocked the best result. That single diagnostic moved crnn-small's 15.40% down to crnn-large's 9.57%.
  5. Evaluated at three levels. Line CER guides training; the line segmenter's count is checked against the ground truth; and page-level CER is measured end-to-end - the number the product actually feels.

How the Technologies Were Used

  • PyTorch - the CRNN reader (CNN feature extractor → bidirectional LSTM) and a custom training loop with best-checkpoint saving, LR scheduling, and anchored resume.
  • CTC loss - alignment-free line recognition with greedy decoding; the design reason the baseline is trustworthy (it emits only what it sees).
  • Hugging Face Transformers / TrOCR - the challenger, a vision encoder-decoder fine-tuned with AMP/fp16, LR warmup + cosine decay, and gradient accumulation for GPU training.
  • PyMuPDF - PDF parsing and layout structuring into ordered text blocks.
  • Tesseract - the printed-text OCR backend, exposed through the same contract as the HTR reader.
  • Qdrant + FastAPI + Claude - vector store for semantic retrieval, service layer, and an agentic RAG loop that answers over retrieved blocks and cites the source.
  • pytest & Colab - 105+ tests (including hermetic and smoke coverage) and a parametrized notebook for the managed GPU training run.

Getting Started

Prerequisites
  • Python 3.11 or higher
  • pip package manager
  • GPU optional - only needed to fine-tune the TrOCR challenger
Installation
git clone https://github.com/Calazansmacchiutti/Stratifile-Agent-PDF.git
cd Stratifile-Agent-PDF
pip install -e .
Running
# validate the whole HTR pipeline end-to-end on CPU (seconds)
python scripts/train_trocr.py --smoke

# train the CRNN baseline locally on CPU
python scripts/train_bressay_local.py --model crnn-large --epochs 12

# fine-tune the TrOCR challenger on GPU (Colab/Kaggle)
python scripts/train_trocr.py --epochs 8 --batch 8

Results & Impact

A Brazilian-Portuguese handwriting reader that stands among published academic baselines despite CPU-only training (9.57% line CER, beating Flor and Bluche), delivered as a 17 MB versioned artifact ready to ship as a small containerized service. Because every stage is isolated by contract, the recognizer can be swapped - the moment the TrOCR challenger clears the gate - without touching the rest of the pipeline. The result is less a single model than a repeatable method for turning scanned documents, typed or handwritten, into retrievable and cited answers.
